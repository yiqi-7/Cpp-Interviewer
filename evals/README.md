# Skill 行为评测

`cases.json` 保存一组可重放用例及验收条件，覆盖触发、讲解、训练和降级。它是待执行的测试语料，不是已经通过的评测报告。Python 单元测试验证语料结构；只有真实 Agent 的运行记录才能证明行为。

## 两种测试分开运行

- **触发测试（`kind=trigger`）**：在新会话中，让目标 Agent 按正常机制发现已安装技能。只发送 `prompt`，不得先要求它读取 Skill，不得把 `expected_mode` 或 `checks` 发给执行者。用宿主的技能选择、文件读取或等价记录确认是否实际加载；仅凭回答像面试答案无法证明触发。宿主不暴露可核验记录时，触发结果标记 `unverified`。
- **执行测试（`kind=execution`）**：可以明确要求读取 `entrypoints` 中对应入口及它引用的相关文件。提供用例的环境前提、`context` 和 `prompt`，不提供验收条件。多个入口分别使用干净会话，比较相同的输出契约，不要求逐字相同。

触发基线至少包含 5 个相关正例和 5 个相近但不相关的反例。正例命中少于 4/5，通常说明描述过窄；反例误触发多于 1/5，通常说明描述过宽。反例应尽量覆盖邻近任务（例如普通 C++ 修 bug 或 CMake 配置），不能只使用完全无关的语言或产品任务。

上面的 4/5 与 1/5 是定位描述问题的诊断线；发布前按清单目标争取正例 5/5 命中、反例 0/5 误触发。两类分数分开报告，说明每个例子是否有宿主激活证据。

`expected_mode=none` 表示此项目不应加载，不禁止宿主使用其他合适技能。`clarify` 表示信息不足时短暂澄清；它不是新的技能入口。

## 隔离状态和依赖

所有会查询、保存或重置训练状态的用例都必须使用临时目录。先将知识索引复制到该目录，再把下面三个变量传入执行 Agent 的实际工具进程，不能只在一段不相连的终端会话中设置：

```powershell
$runRoot = Join-Path $env:TEMP ('cpp-interviewer-eval-' + [guid]::NewGuid().ToString('N'))
New-Item -ItemType Directory -Path $runRoot | Out-Null
Copy-Item -LiteralPath 'skills/coach/index/knowledge_index.json' -Destination (Join-Path $runRoot 'knowledge_index.json')
$env:CPP_INTERVIEWER_HOME = $runRoot
$env:CPP_INTERVIEWER_DB = Join-Path $runRoot 'coach.sqlite'
$env:CPP_INTERVIEWER_INDEX = Join-Path $runRoot 'knowledge_index.json'
```

以上示例在独立评测终端、仓库根目录执行；结束后关闭该终端，或恢复这些变量之前的值。不要改写系统 `HOME` / `USERPROFILE`、全局 Python 配置或真实技能安装。每个有状态用例、每个入口及每次重复运行使用独立目录。用例需要训练记录时，只向临时数据库写入固定的合成题目与答案，并保存其初始状态。

CLI 缺失用例通过限制执行者工具能力来构造，不卸载 Python 或破坏 PATH。资料缺失用例使用临时副本，不删除用户书籍。状态变更必须核对工具调用及数据库前后差异；只听 Agent 说“已保存”不算通过。

## 执行和判分

1. 记录待测代码版本、Agent 与模型版本、工具能力、操作系统、工作目录及入口。区分仓库根目录启动、其他项目目录启动和已安装环境。
2. 对每个用例建立新上下文，满足 `preconditions`。先提供 `context`，再发送 `prompt`，保留完整回复与工具轨迹。
3. 由独立评审者逐条检查 `checks`，填写通过、失败或无法验证，附证据位置。涉及 C++ 事实时依据语言规则和实际证据判断；示例标题、关键词命中或 JSON 字段齐全都不能替代正确性。
4. 对多个入口的用例分别执行，核对相同意图和格式约束是否得到遵守。Coach 保存用例核对新增记录数、题目、答案和评价，首次出题、退出、未确认重置用例核对没有误写入。
5. 固定模型和工具条件重复运行。首次可做小规模冒烟并明确所覆盖用例；正式基线建议每项至少三次。评分用例还需观察同一答案的理由、总分与等级是否稳定。

执行者只获得执行所需信息。验收条件、旧版得分和期望优胜版本留给评审者，减少提示答案和作者偏差。复杂或高成本用例可以分批完成，未执行部分保留 `not_run`。

## 结果记录约定

真实结果写到评测工作目录，由维护者选择是否归档；本目录不预填通过率或模拟 transcript。至少保留以下内容：

| 字段 | 记录内容 |
|---|---|
| 身份 | `case_id`、`run_id`、重复序号、入口、测试日期 |
| 版本与条件 | Git commit；有未提交修改时附 diff/快照；Agent、模型、工具、OS、工作目录与状态夹具 |
| 实际输出 | transcript 和工具轨迹文件；有状态用例的运行前后快照 |
| 判分 | 每条验收条件的结果、证据与原因；评审者或评审模型 |
| 成本 | 耗时、输入/输出 Token；宿主未提供的数据填 `null` 并说明原因，不估算成实测 |
| 总状态 | `pass`、`fail`、`unverified` 或 `not_run` |

只有必需验收条件均有证据通过时，总状态才是 `pass`。存在明确失败标 `fail`；已运行但证据不足标 `unverified`；未运行标 `not_run`。如果缺少任一 `required_evidence` 类型（包括宿主不提供激活轨迹、工具轨迹或状态快照），必须标 `unverified`，不能用回答文本推断缺失证据。同时报告四类数量和完成覆盖率，不能把无法验证或未运行项目悄悄排除后声称“全通过”。

## 比较与回归

- **无 Skill 对照**：在干净环境禁用本项目技能，执行相同任务，比较正确性、意图遵守、信息密度、工具误用和成本。只有对照结果显示可重复的质量提升时才声称 Skill 改善了输出；若结果相近则报告持平。自动触发率只在正常启用技能的条件下计算。
- **版本 A/B**：相同输入、模型、工具、夹具和重复次数，输出随机标记 A/B 后独立评审。两个版本使用不同状态目录，避免训练记录影响后一个版本。
- **Benchmark**：按重复轮次报告任务通过率及均值/标准差；同时报告触发正例命中与反例误触发、耗时、Token、运行次数和样本数。小语料的高分不代表所有场景可靠。
- **回归时机**：修改描述、回答规则、评分依据、安装路径或模型版本后，重跑受影响用例；发布前跑完整的适用集合。
- **跨 Agent**：分别记录每个 Agent 的加载、触发、讲解、训练及持久化结果。文件可复制、静态测试通过、单个宿主的子代理冒烟，都不能替代其他 Agent 的实测。

## 检查语料本身

```bash
python -m pytest -q tests/test_skill_evals.py
```

此命令检查用例 ID、必要字段、入口路径、覆盖类别和证据要求，不调用模型，也不产生行为通过率。现有数据库、调度器和安装测试继续保留其工程测试职责。
